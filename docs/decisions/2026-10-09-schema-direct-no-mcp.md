# MCP・索引を持たず、自然文のスキーマをフックが注入する

## 背景

実エージェントの自動E2E（起票・検索・移行）で、次のことがわかった。

- エージェントは、MCP の `list_folder` をほとんど使わず、`schema.yaml` を直接読み、確認は `ls` / `find` で済ませた。専用ツールを使わせる文面の工夫は、効きにくい。
- 周辺ツール（MCP サーバー、SQLite 索引、同期エンジン、`description.md` の規則）の管理コストは、価値を上回った。`description.md` の欠落は、起票の失敗の原因でもあった。

zoomdoc の価値は、残すべき文書をスキーマで宣言でき、確実に想起させられること。周辺ツールはその手段でしかない。

## 決定

1. MCP サーバー、SQLite 索引、同期エンジンを廃止する。正本はファイルシステムだけとする。
2. スキーマは、フォルダのパス（キー）と `description`（自然文）だけを持つ。置く文書の種類・名前・書くとき・雛形は、説明に書く。`filename` / `naming` / `format` / `trigger` の欄は持たない。
3. フックが、スキーマをそのまま（コメントと空行を除いて）、セッション開始時とスキーマ変更時に注入する。要約も、トリガーのハッシュIDも使わない。フォルダの役割は `description` が持ち、`description.md` は要らない。
4. 探索は、スキルが示すコマンド（`title` と `description` の一覧）で行う。
5. 移行（`migrate.js`）は、現行のまま残す。

## 結果

- 構造化したスキーマ（要約を注入）と、自然文のスキーマ（そのまま注入）を、同じシナリオで比べた。
- 自然文のスキーマ: 起票 10/10（命名の文面を直した後）、重複確認 5/5、検索 5/5、移行（標準・ルート別名）6/6。構造化と同等の合格率で、新規入力トークンは起票で約15%、重複確認で約10%減った。
- 検知（リンク切れ・Frontmatter・フォルダの散らばり・未許可フォルダ）は、パスしか読まないので、影響を受けない。

数値は [benchmark.md](../evaluation/benchmark.md)。

## 注意

- スキーマが大きくなると、注入のトークンが増える。いまは約4.8KB。フォルダが数十を超えるなら、見直す。
- 自然文は読み違えられることがある（例:「既存が連番ならそれに合わせる」を、既存が無いのに連番にした）。迷いやすい決まりは、条件を明確に書く。
- 固定名の存在確認や命名の機械検査はできない。説明と実態のずれは、`/doc-lint` の調査で点検する。
- 散文の指示に頼るので、守られない回はありうる。E2E の合格率で見続ける。
