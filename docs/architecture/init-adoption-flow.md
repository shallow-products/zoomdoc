# 既存プロジェクトへの導入フロー（/zoomdoc:init）

多くのプロジェクトは、文書やフォルダがすでにある状態で zoomdoc を導入する。そのため導入は「標準のスキーマを置いてから合わせる」のではなく、**構成の決定を先に、必須の対話で行い、承認後にスキーマを確定してから導入する**。文書がほとんどない初期状態でも、この対話は省略しない。経緯は [Issue #18](https://github.com/shallow-products/zoomdoc/issues/18)。

## 原則

- **黙って決めない**: 推奨どおりに進める場合も、実行前に「何を、なぜ、どうするか」を伝える。すべての選択は、ユーザーの選択として記録する。
- **構成はディレクトリツリーで見せる**: 各フォルダに1行の説明と既存の文書数を付ける。3つの選択肢は同じ形式で並べる。
- **何も書かないうちに承認を得る**: スキーマの書き換えは、変更前後のツリー差分を見せて承認を得てから行う。
- **再実行できる**: 途中で止まっても、やり直しても安全にする。

## 提示のルール

実際に使ったところ、報告が長く、何を確認したいのか、何がどう変わるのかが読み取りにくかった。そこで、各メッセージは次の形にする（`commands/init.md` に同じ内容を定める）。

- **質問を先頭の1文で示す**。背景はその後に置く。
- **1メッセージ1判断**。判断の要らない事実は1行にまとめるか省く。既定の扱い（対象外にするフォルダなど）は、質問と同じ行で述べ、別の質問にしない。
- **現在と変更後をツリーの差分で示す**（`+` 新規、`~` 変更、`-` 削除、無印は変更なし）。変更がなければ「変更なし」と1行で言う。言葉だけで変更を説明しない。
- **選択肢は短く**: ラベル、変わること（1行）、その結果（1行）。理由は選択肢の中に書かず、**最後の選択肢の後に、推奨とその理由**（「おすすめは1です。理由は…」）を1〜2行で書く。
- **各回答の次の動き**を1行で示す（例: 「1を選ぶと何も書き込まないので、段階3と4を省く」）。
- 既にスキーマがある場合は、段階2の問いを「このままにするか、設計し直すか」にする。

## 5段階

| 段階 | 内容 | ユーザーの関与 |
|---|---|---|
| 0. 事前確認 | git の状態、既存の `.zoomdoc/`、モノレポの有無を確認して結果を通知する | 通知のみ |
| 1. 現状の把握 | 既存の文書を一覧にする（パス、種別の推定、件数）。ユーザーが設計したと見られる文書と、生成物・一時ファイルを区別して示す | 一覧を確認 |
| 2. 構成の決定（必須） | 3つの選択肢から選ぶ。文書が0件でも省略しない | 必ず選択 |
| 3. スキーマの確定 | 選んだ構成からスキーマの案を作り、ツリーの差分を見せる。承認後に書き換える | 必ず承認 |
| 4. 導入 | スキーマと雛形を配置する。必要なら文書を移行する（ドライラン、承認、適用、ロールバック） | 承認 |
| 5. 完了 | 診断を実行し、結果と残った違反を通知する | 通知のみ |

## 段階2の選択肢

- **推奨構成**: zoomdoc の標準のフォルダ構成。
- **ユーザーの希望の構成**: 希望を聞いて、フォルダ構成と命名を決める。
- **現在の構成を維持**: 既存の構成を読み取り、それに合わせたスキーマを作る。

提示の例:

```text
推奨構成（zoomdoc の標準）

docs/
├── product/        何を作るか（ビジョン、要件）
├── decisions/      なぜそう決めたか（ADR、1決定1ファイル）
├── architecture/   どう作られているか（構成、技術スタック）
└── guides/         手順（セットアップ、運用）
```

```text
現在の構成を維持（検出した構成から作成）

docs/
├── design/         12 件 ← 既存のフォルダ。アーキテクチャとして扱う
├── howto/           5 件 ← 既存のフォルダ。ガイドとして扱う
└── notes/          31 件 ← 既存のフォルダ。参考資料として扱う
```

段階3の差分の例:

```text
  docs/
+ ├── decisions/      新規
~ ├── design/         説明を更新（architecture 相当）
  └── howto/          変更なし
```

## 実装

- `commands/init.md` が、この5段階の手順と、全段階共通のルール（黙って決めない、ツリーで見せる、承認前は何も書かない）を定める。
- `scripts/init.js survey` が段階0と1（読み取りのみ。git の状態、既存のスキーマ、モノレポの兆候、文書の所在と件数）、`scripts/init.js layout` が推奨構成のツリー、`scripts/init.js --schema-file <path>` が段階4（承認済みのスキーマを配置する。`folders` のないスキーマは拒否）を担う。ツリーの描画は `scripts/layout.js`、調査は `scripts/survey.js`。
- 段階2の「ユーザーの希望の構成」と「現在の構成を維持」のツリーと、段階3の差分は、エージェントがスキーマ案から作って見せる。
