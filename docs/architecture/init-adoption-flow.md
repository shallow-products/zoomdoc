# 既存プロジェクトへの導入フロー（/zoomdoc:init）

多くのプロジェクトは、文書やフォルダがすでにある状態で zoomdoc を導入する。そのため導入は「標準のスキーマを置いてから合わせる」のではなく、**構成の決定を先に、必須の対話で行い、承認後にスキーマを確定してから導入する**。文書がほとんどない初期状態でも、この対話は省略しない。経緯は [Issue #18](https://github.com/shallow-products/zoomdoc/issues/18)。

## 原則

- **黙って決めない**: 推奨どおりに進める場合も、実行前に「何を、なぜ、どうするか」を伝える。すべての選択は、ユーザーの選択として記録する。
- **構成はディレクトリツリーで見せる**: 各フォルダに1行の説明と既存の文書数を付ける。3つの選択肢は同じ形式で並べる。
- **何も書かないうちに承認を得る**: スキーマの書き換えは、変更前後のツリー差分を見せて承認を得てから行う。
- **再実行できる**: 途中で止まっても、やり直しても安全にする。

## 提示のルール

実際に使ったところ、報告が長く、何を確認したいのか、何がどう変わるのかが読み取りにくかった。そこで、各メッセージは次の形にする（`skills/init/` に同じ内容を定める）。

- **質問を先頭の1文で示す**。背景はその後に置く。
- **1メッセージ1判断**。判断の要らない事実は1行にまとめるか省く。既定の扱い（対象外にするフォルダなど）は、質問と同じ行で述べ、別の質問にしない。
- **現在と変更後をツリーの差分で示す**（`+` 新規、`~` 変更、`-` 削除、無印は変更なし）。変更がなければ「変更なし」と1行で言う。言葉だけで変更を説明しない。
- **選択肢は短く**: ラベル、変わること（1行）、その結果（1行）。理由は選択肢の中に書かず、**最後の選択肢の後に、推奨とその理由**（「おすすめは1です。理由は…」）を1〜2行で書く。
- **各回答の次の動き**を1行で示す（例: 「1を選ぶと何も書き込まないので、段階3と4を省く」）。
- 既にスキーマがある場合は、段階2の問いを「このままにするか、設計し直すか」にする。

## メッセージの構造

判断を求めるメッセージは、次の順序を既定の形にする。やり取りは原則に従って柔軟に変えてよいが、質問を先頭に、推奨を選択肢の後に置くことは守る。見出しの文言は、ユーザーの言語に合わせる。

```text
【質問】     何を決めてほしいかを1文で
【現状】     判断に要る事実だけを1〜2行で
【選択肢】   番号つき。ラベル／変わること／その結果。変更はツリーの差分で
【おすすめ】 どれか、と理由を1〜2行で
【次の動き】 回答ごとに何が起きるかを1行ずつ
```

判断が要らない段階1は、【現状】を1〜2行で述べて先へ進む。段階5は、【決めたこと】【書き込んだもの】【残った問題】にする。

## ビフォーアフターを出す時点

| 時点 | 示すもの |
|---|---|
| 段階2の【選択肢】 | 選択肢ごとに、現在のフォルダからどう変わるか（プレビュー） |
| 段階3の承認の前 | `schema.yaml` に書き込む正確な変更 |
| 段階4で文書を移す前 | `dry-run` の移動の一覧（同じ `+ ~ -` の形） |
| 段階5の【書き込んだもの】 | 実際に書いた内容（承認した内容と見比べる） |

## 5段階

| 段階 | 内容 | ユーザーの関与 |
|---|---|---|
| 1. 現状の把握 | git の状態、既存のスキーマ、モノレポの兆候を確認し、既存の文書を一覧にする（件数、生成物や一時ファイルとの区別）。ユーザーが設計したと見られる文書は、既定でそのままにする | 通知のみ（判断が要るときだけ質問） |
| 2. 構成の決定（必須） | 3つの選択肢から選ぶ。文書が0件でも省略しない | 必ず選択 |
| 3. スキーマの確定 | 選んだ構成からスキーマの案を作り、ツリーの差分を見せる。承認後に書き換える | 必ず承認 |
| 4. 導入 | スキーマと雛形を配置する。必要なら文書を移行する（ドライラン、承認、適用、ロールバック） | 承認 |
| 5. 報告 | 診断を実行し、決めたこと、書き込んだもの、残った問題を報告する | 通知のみ |

選んだ構成でスキーマが変わらない場合は、段階3と4を省く。段階の番号は `skills/init/SKILL.md` の一覧が唯一の定義で、ファイル名には番号を使わない（段階の追加や入れ替えで、参照を直さずに済ませるため）。

## 段階2の選択肢

- **推奨構成**: zoomdoc の標準のフォルダ構成。
- **ユーザーの希望の構成**: 希望を聞いて、フォルダ構成と命名を決める。
- **現在の構成を維持**: 既存の構成を読み取り、それに合わせたスキーマを作る。

提示の例:

```text
推奨構成（zoomdoc の標準）

docs/
├── product/        何を作るか（ビジョン、要件）
├── decisions/      なぜそう決めたか（ADR、1決定1ファイル）
├── architecture/   どう作られているか（構成、技術スタック）
└── guides/         手順（セットアップ、運用）
```

```text
現在の構成を維持（検出した構成から作成）

docs/
├── design/         12 件 ← 既存のフォルダ。アーキテクチャとして扱う
├── howto/           5 件 ← 既存のフォルダ。ガイドとして扱う
└── notes/          31 件 ← 既存のフォルダ。参考資料として扱う
```

段階3の差分の例:

```text
  docs/
+ ├── decisions/      新規
~ ├── design/         説明を更新（architecture 相当）
  └── howto/          変更なし
```

## 実装

`init` は、コマンドではなくスキルとして置く（コマンドとスキルは同じ仕組みで、補助ファイルを置けるスキルが公式に推奨されている）。入口を短くし、段階ごとの詳細は、その段階に入ったときにだけ読む（段階参照式）。

```text
skills/init/
├── SKILL.md                入口: 共通ルール、段階の一覧（番号、名前、読むファイル）、ビフォーアフターを出す時点
└── references/
    ├── survey-project.md       1. 現状の把握
    ├── choose-layout.md        2. 構成の決定
    ├── approve-schema.md       3. スキーマの確定
    ├── deploy-and-migrate.md   4. 導入（移行プロトコルを含む）
    ├── report-result.md        5. 報告
    └── report-formats.md       全段階のレポートの書式と出力例
```

- ファイル名は、動詞＋目的語にする。単語1つ（`schema.md` など）だと、`skills/schema/` と紛らわしく、内容も分からないため。
- `scripts/init.js survey` が段階1（読み取りのみ。git の状態、既存のスキーマ、モノレポの兆候、文書の所在と件数）、`scripts/init.js layout` が推奨構成のツリー、`scripts/init.js --schema-file <path>` が段階4（承認済みのスキーマを配置する。`folders` のないスキーマは拒否）を担う。ツリーの描画は `scripts/layout.js`、調査は `scripts/survey.js`。
- 段階2の「ユーザーの希望の構成」と「現在の構成を維持」のツリーと、段階3の差分は、エージェントがスキーマ案から作って見せる。
