## 2. 測り方と、記録のしかた

1. **動的E2E**: `docker compose run --rm zoomdoc-dev npm run test:e2e`。`claude` CLI が使える環境が要る（使えないシナリオは、スキップと表示される）。スコアの算出は [trajectory.md](trajectory.md) の4指標に従う。
   **スキルの通し（起票・移行）**: `docker compose run --rm zoomdoc-e2e node tests/e2e/run.js`。手順と出力は `tests/walkthrough/README.md`。出る `report.md` の「benchmark.md に足す行」を記録する。
2. **記録**: 行を足す。過去の行は書き換えない。必ず「測定日・版（または commit）・測定時の実装の違い」を添える（実装が変わると、数値の意味が変わるため）。
3. **更新する時機**: フックやスキルの設計を変えたとき。変更が測定対象の挙動に及ぶなら、動的E2Eの再測定を行う。

## Hookの所要時間(#54、2026-10-10)

`tests/perf/hook_timing.js`で測る。コンテナ内にコピーした静かな環境で、各25回の中央値(ms)。Node空起動は約19ms。最初に測った表は、ホスト負荷によるノイズ(p95が中央値の2倍)が大きく、判断に使えなかったため、この表に置き換えた。

UserPromptSubmitで、毎プロンプト走る処理(変更なし)の合計:

| 文書数 | 旧(2プロセス: detect + sync) | 新(run.js、1プロセス) |
|---|---|---|
| 10 | 47 | 28 |
| 100 | 46 | 41 |
| 1000 | 61 | 46 |

SessionStart(--force)で、未解決の指摘がある場合の全走査(新):

| 文書数 | 全走査 |
|---|---|
| 10 | 35 |
| 100 | 53 |
| 1000 | 157 |

- 1プロセス化で減ったのは、起動1回分(約20ms)だけ。毎プロンプトの合計は、旧より約20ms短い。
- 全走査は、文書数に比例する(約0.13ms/件)。1プロセス化では変わらない。1000件で約150ms。
- 変更が無いときは、`stat`だけの署名比較で走査を省く。1000件でも約45ms(うち起動が約20ms)。
- 目標150msは、1000件の全走査でほぼ限界。100〜200件の想定なら、全走査も53ms以下で、ネイティブ化は不要。
- 起動の固定費は、検知を足しても1回で済む。検知の追加(#57)は、走査の中で行えば、プロセスは増えない。

## スキーマの文書の行(`update`・`remove`)の読み取り(#63、2026-10-10)

構造化したスキーマ(#61)で、`supersede`・`archive`を各1回。いずれも成功。

| シナリオ | 期待 | 結果 |
|---|---|---|
| supersede(15分→30分に変える) | 既存のADRを書き換えず、新しいADRを作る | 既存は不変。新しいADR(`2026-10-10-access-token-expiry.md`)を作り、覆した決定にも触れた |
| archive(設計メモが決定になった) | `remove`の条件に従い、`docs/archive`へ移し、旧リンクを直す | `zoomdoc:move`に従い、移動と旧リンクの修正を行い、doc-lintも通した。Redisの決定のADRが無いことも指摘した |

- 各1回なので、傾向の確認まで。繰り返し(n=3以上)での確認は、リリース前に行う。
- 副産物: supersedeで、関係の薄い既存ADRも読んだ(無駄な読み込みは小さい)。
